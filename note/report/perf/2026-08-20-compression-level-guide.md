# 批次 63 报告（2026-08-20）— 网络压缩级别选型指南（带宽主题运营收尾）

配套交付物：`/paper netstat`（0225，测）+ `paper-global.yml` `misc.compression-level`（调）。本报告给出"测了之后怎么调"的决策数据。

## 数据（CompressionLevelBench，JDK Deflater 21.0.10，Windows/JDK 回退路径；生产 Linux 为 libdeflate）

### 选型矩阵（30 次平均，roundtrip 完整性 ALL OK）

| 载荷（模型） | level 1 | level 3 | level 6（默认） | level 9 |
|---|---|---|---|---|
| **chunk**（24 section 调色板方块态，~393KB） | 4.10× / 2.87ms | 4.43× / 5.28ms | **4.90× / 15.5ms** | 4.88× / 39.2ms |
| **text**（ASCII 聊天/计分板，1KB） | 4.10× / 11.7µs | 4.26× / 10.2µs | 4.56× / 12.5µs | 4.56× / 13.2µs |
| **light**（半随机 nibble，~49KB，保守下界） | 1.69× / 0.57ms | 1.69× / 0.88ms | 1.72× / 1.37ms | 1.72× / 1.35ms |

（格式：压缩比 / 单次编码耗时）

### JMH（`-wi 3 -i 5 -f 2 -r 1s -w 1s`，avgt ns/op）

| 方法 | ns/op | 备注 |
|---|---|---|
| encode_chunk_level1 | 2,838,434.729 ± 44,694.829 | chunk 载荷（~393KB） |
| encode_chunk_level6 | 15,549,552.431 ± 541,106.033 | 默认级 |
| encode_chunk_level9 | 37,500,774.815 ± 180,878.809 | 比 level 6 慢 2.4×、压缩比零增益 |
| encode_light_level6 | 1,363,124.767 ± 22,426.153 | 低熵载荷 |

与矩阵一致：level 1→6→9 的 chunk 编码时间 2.8ms→15.5ms→37.5ms（1→5.5→13.2×），压缩比 4.10→4.90→4.88×——**6 以上纯付 CPU 不买字节**。

## 结论（可直接执行）

1. **带宽紧张的服务器不要把 level 调到 6 以上**：区块型载荷（出站流量大头）level 6→9 压缩比**零增益**（4.90×→4.88×，噪声内）而编码 CPU **2.5×**。level 9/12 是纯 CPU 浪费（对 MC 载荷）。
2. **CPU 紧张（高并发跑图/区块重传）可降到 3**：省 66% 压缩 CPU，代价仅 +9% 字节（4.90→4.43×）。level 1 再省一半 CPU 但 +19% 字节，仅限极端 CPU 瓶颈。
3. **光照/低熵载荷对 level 完全不敏感**（1.69-1.72× 持平）——level 只买 CPU 不买带宽。
4. **操作闭环**：`/paper netstat` 看每玩家出站 B/s 基线 → 调 level → 再看 netstat 验证字节变化与 MSPT 变化。
5. 诚实边界：本机为 JDK 回退后端，**绝对时间不可直接套用到 libdeflate**（快约一个量级）；**相对趋势（6 以上无带宽收益、3 是 CPU 高效前沿）在两后端间可迁移**（同族 DEFLATE 算法、级别语义一致）。区块模型压缩比 4-5×（真实区块冗余更高、比值更高），趋势不变。

## 其他

- threshold（server.properties `network-compression-threshold`，默认 256）与 0217 的零拷贝快路互补：低于阈值的包完全跳过压缩（现在也零拷贝）；阈值本身是另一个带宽/CPU 旋钮（调大→更多包免压缩省 CPU、费带宽），可用同一 netstat 方法评估。
