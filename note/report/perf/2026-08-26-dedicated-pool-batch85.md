# 批次 85 报告（2026-08-26）— 专用登录 datafix 池假设检验（否决）+ /mspt 度量基建勘察

主题：批次 84 判例的推论验证。datafix 下放的三种共享池形态（IO 池 / worker 池 HIGHEST /
worker 池 NORMAL）均被实测否决后，剩余假设是：**专用登录池**（1-2 线程、NORM-1 优先级、
不与区块管线共享任何资源）能否既保住主线程减负又不引入竞争——批次 84 三难的正解推论。

## 1. 实现（0250，已撤）

`PapoLoginDatafixPool`（src/main 直提交，cores/8 clamp[1,2] daemon 线程 NORM-1）+
`PlayerDataStorage` 两阶段链（读 IO 池 → fix 专用池，消费点 bounded get + 读升级）。

## 2. 实测否决（第四形态）

20-bot fat-dat burst（与批次 84 同口径，0.55.0-with-0250 vs 0.54.0）：

| 版本 | datafix 位置 | burst lastSpawn（3 轮） |
|---|---|---|
| v4（批次84 终态） | 主线程消费点 | 3394/3656/3856（mean 3635） |
| **v6（本批：专用池）** | 专用 2 线程池 | **3935/4109/3993（mean 4012，比 v4 慢 ~380ms）** |

机制解释：20 个并发 join 的消费点在 2 线程修复队列上排队（队尾 bot 等待 ~10×修复时长）；
同时主线程不再被 datafix 串行化 → 全部 bot 同时压到区块加载通路上（需求扎堆）。
**结论**：主线程串行 datafix 的"自然限流"本身就是该场景的最优调度——四种放置形态
（IO 池/worker 池×2/专用池）全部实测劣于留在主线程，v4 判例终局加固。0250 已从补丁
序列摘除（内部历史 rebase-drop，批次 29 先例），`PapoLoginDatafixPool` 删除。

## 4. /mspt 度量基建勘察（平台限制，如实留档）

Paper 自带 `/mspt`（5s/10s/1m 三窗 avg/min/max，`MSPTCommand`）。BurstJoinVerify 已内置
发送与捕获；**但 zh-CN Windows + 管道控制台环境下 ◴ 数字行不输出**（表头可见、数字行
缺失；MsptProbe 最小复现实证，92 行日志中仅表头在场）——jline 非 tty 管道的字符编码/写
入路径限制。后续如需 MSPT 数据：Linux/tty 环境下同一捕获可用，或改读 `tickTimes*` 需要
服务器侧改动（超出本轮范围）。MsptProbe 保留为诊断工具。

## 5. 判例

- **"自然限流"可能是隐式最优调度**：把串行工作并行化后，下游（区块管线）的瞬时需求
  扎堆可能吃掉全部收益——判断并行化收益时必须看下游吞吐是否弹性。
- 负结果轮同样构成证据链：四次放置实验后，"登录 datafix 留主线程"从保守选择升格为
  实测最优。
