# 批次 86 报告（2026-08-26）— 多核调度系列宏观 worldgen 校准（0.52.0 系列前 vs 0.55.0 系列后）

主题：批次 78/80 的池预算改动（netty 4→8、regionIO 1→4、worker 8→12）此前仅有合成任务级
证据（批次80 真实池 1.48× + tick 探针 0 偏差）与 boot 集成验证（批次81），宏观端到端因
"forceload 无完成信号"被否决。本批用既有 burst 基建补上宏观口径：**fat .dat 的 Pos 指向
远方未生成区块（10000,10000）**，20 bot 并发 join 即触发真实 worldgen 突发（每 bot 出生
半径 3 × 49 chunk 需从空世界生成），现代 DV（4671）隔离 datafix 噪声。

## 方法

[MakeFatPlayerDat](../../../benchmark/src/papo/bot/MakeFatPlayerDat.java) 增 `PAPO_FAT_POS_X/Z`
覆盖（默认出生点近 spawn）；BurstJoinVerify 同口径（fresh 世界/固定 seed/20 bot 屏障并发/
双向序），0.52.0（批次78 前：4/1/8）vs 0.55.0（系列后：8/4/12）。

## 结果（10+9 轮，全部门绿：exit 0 / 零门错误 / dat 合法）

| jar | lastSpawn 全样本 | mean |
|---|---|---|
| 0.52.0（n=9） | 3379/3183/3518/3877/3839/3711/3442/3242/3210 | **3489ms** |
| 0.55.0（n=10） | 3134/3314/3265/3280/3635/3791/3929/3618/3511/3146 | **3462ms** |

**Δ = −27ms（~0.8%），轮间 σ≈250ms——统计持平**。双向序各 run 内部方向不稳定
（A: −123ms 偏 0.55；D: +127ms 偏 0.52）。

## 归因（机制级解释）

join-gen 突发的关键链是**主线程串行面**而非 worker 面：20 bot 的配置阶段处理 +
placeNewPlayer 逐 bot 在主线程串行（~150ms/bot ≈ 3s 主导项），而 49-chunk 生成总量仅
~1s（8 worker ≈ 125ms 墙钟、12 worker ≈ 83ms——Δ~40ms 被淹没）。与批次 84/85 的
"自然限流"观察同源：**该负载的端到端节奏由主线程管线决定，池预算在此场景无放大面**。

## 结论与校准

1. **不否定批次 78/80**：worker 曲线的 1.48× 是 worker 面真实（合成直测 + tick 探针
   0 偏差），其收益场景是**持续区块需求**（探索/跑图，无 join 串行面稀释）；本批补上的
   是宏观 join-gen 口径的诚实校准——端到端持平。
2. **核心洞察再强化**：本服务器的多核利用率瓶颈常在主线程串行面（join 管线、事件处理），
   而非池预算；后续多核工作的最高价值面是**减少主线程串行工作**（如批次82 的读侧下放），
   而非继续调池。
3. 工程附带：MakeFatPlayerDat 远坐标覆盖 + BurstJoinVerify 良性门统一
   （`isBenignCloseRace`：本机 locale socket 文案经 sun.jnu.encoding 层产出乱码问号串，
   `-Dfile.encoding` 管不到——判例留档）。
